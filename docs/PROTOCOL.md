# EDIFIER Halo Soundbar 控制协议（逆向还原）

本文档描述如何直接通过 USB 控制 **EDIFIER Halo Soundbar**（漫步者花再 Halo 音箱），
全部内容来自对官方客户端 **EDIFIER TempoHub v1.3.0** 与官方 Android 客户端
**EC 8.5.2** 的逆向分析，并在真机上逐条验证。

> **适用范围**：本文所有协议细节**仅在 Halo Soundbar（USB PID `A063`）上实测确认**。
> 同系列其他型号（Halo Space / Halo Soundbar Max / Halo 2.0 SE 等）共享同一套 EC
> 协议框架，但功能位图、灯效表、EQ 模型均不相同，本文的**取值**不可直接套用。

---

## 1. 设备识别

| 项目 | 值 |
|---|---|
| USB VID | `0x2D99`（Jieli 杰理） |
| USB PID | `0xA063` |
| 产品名 | Halo Soundbar |
| 官方产品号 `ProductId` | `41059` |
| 厂商标识 | `edifier` |
| `HeadsetType` | `5` |
| 出厂固件 | `1.0.1` |

设备暴露 4 个 USB 接口：

| 接口 | 类别 | 用途 |
|---|---|---|
| `MI_00` | MEDIA（USB Audio Class） | 音频播放 |
| `MI_03` | HID（usage page `0x000C`） | 多媒体按键 |
| `MI_04` Col01 | HID（usage page `0xFF13`） | **不可用**：所有写入被拒绝 |
| **`MI_04` Col02** | HID（usage page `0xFF14`） | **控制通道**，64 字节报文 |

**必须打开 Col02（usage page `0xFF14`）**，Col01 看起来更像"厂商自定义"但实际不接受写入。

## 2. 传输层

### 2.1 打开方式

用 Windows HID API（`CreateFile` / `WriteFile` / `ReadFile`），两个要点：

1. **写入句柄用同步模式即可**（`FILE_ATTRIBUTE_NORMAL`）。
2. **读取必须用 overlapped 模式 + `CancelIoEx` 超时**。同步 `ReadFile` 会永久占用一个
   系统辅助线程，该线程会**抢走报文**，导致后续读取全部失败。

### 2.2 报文格式

发往设备的报文**补齐到 64 字节**（HID output report）。

### 2.3 一个坑：`ERROR_IO_PENDING` 的数值

overlapped `WriteFile` 的 pending 返回码是 **`0x800703E5`**（`ERROR_IO_PENDING`），
**不是** `0x800700E5`。写错会导致所有写入被误判为失败。

## 3. EC 协议帧

### 3.1 帧结构

```
2E  AA  EC  <cmd>  <len_hi>  <len_lo>  <payload...>  <crc>
```

| 字段 | 说明 |
|---|---|
| `2E` | 起始标记（固定） |
| `AA` | 帧头（固定） |
| `EC` | 设备类型。`DEVICE_TYPE_TRANS_MAP = [0xEC, 0xED]`，对应 `device_index` 0/1 |
| `cmd` | 命令字节 |
| `len` | payload 长度，**大端** |
| `payload` | 载荷 |
| `crc` | `sum(bytes[1 .. 最后一个 payload 字节]) & 0xFF`（从 `AA` 开始累加） |

### 3.2 响应

响应以 `2F` 开头（**实机只观察到 `2F`**；`0x55` 属于 EHM 协议族，EC 设备不发，
不要接受它，否则噪声会被当成有效应答）。

**实测响应样例**（`0x65` 的应答，补齐到 64 字节）：

```
2F BB EC 65 00 04 02 00 00 40 52 00 00 ...
↑  ↑  ↑  ↑  ↑     ↑           ↑
标记 ？ 设备类型 命令 长度(大端)  载荷   末字节
```

配对依据是**命令字节相同**。非匹配帧需要暂存而不是丢弃——设备会主动推送状态变更。

#### 两个"看起来能校验、实际不能"的陷阱

实现中曾试图加强校验，**结果把真机全部应答都拒掉了**，值得记录：

1. **`data[1]` 不是常量**。新打开句柄时观察到的是 `2F AA EC …`，
   但正常运行时设备发的是 `2F **BB** EC …`。**不能对 `data[1]` 做等值判断**。
2. **末字节不是本文档 §3.1 那个 CRC**。把 `checksum()`（从 `AA` 起累加到最后一个载荷字节）
   算出来与末字节比对，**实机全部不吻合**。说明应答用了另一套校验方式，
   在搞清之前**不要校验它**。

因此当前实现只校验**标记字节 `0x2F`** 和**设备类型 `EC`/`ED`**，
配对仍需命令字节一致。这是保守但可用的强度；想进一步加强必须先搞清应答校验方案。

### 3.3 协议族选择（重要）

官方客户端里存在**两套**协议：

- **EHM 协议**：分块 + JSON，`ENABLE_PACKET_BUFFER = True`
- **EC 协议**：裸字节，`ENABLE_PACKET_BUFFER = False`

判定链路：

```
HeadsetType == 5  →  DEVICE_TYPE_MAP['SPEAKERBOX']  →  device_type = 'EDIFIER'
                  →  ECDeviceFactory                →  裸字节 EC 协议
```

**Halo 走 EC 协议**。早期误实现 EHM 协议浪费了大量时间。

## 4. 命令参考

### 4.1 握手与状态

| 命令 | 名称 | 请求 | 响应示例 | 说明 |
|---|---|---|---|---|
| `0x65` | `BASE_FUNCTION` | 无 | `[02 00 00 40]` | 能力握手：版本 2、加密 0、最大长度 64 |
| `0xD8` | `DEVICE_FUNCTION` | 无 | 22 字节位图 | 功能位图，见 §5 |
| `0xF2` | `DEVICE_STATUS` | 无 | `[04 00 00 64 00 00]` | 设备状态 |
| `0xC6` | `VERSION` | 无 | `[01 00 02]` | **固件版本**，见下 |

**`0x65` 是健康探测的首选**：响应短、无副作用，可用于判断链路是否存活。

#### 固件版本（`0xC6`）

命令号是 **`0xC6`**（官方 `driver.version_query` 里的 `CM_C6`）。
命令表里另有 `0x9D`，但**设备不响应它**——照命令表实现会得到"不支持"的错误结论。

解析规则（`version_query_parse`）：**payload 每个字节是一个版本段，用 `.` 连接**。

```
响应 [01 00 02]  →  "1.0.2"
```

注意产品表里的 `LastFirmwareVersion` 是**出厂**版本（Halo 为 `1.0.1`），
与设备当前回报的版本可能不同（实测设备已升到 `1.0.2`）。以设备回报为准。

### 4.2 音量

| 命令 | 方向 | 载荷 | 响应 |
|---|---|---|---|
| `0x66` | 读 | 无 | `[max, current]`，Halo 为 `[16, n]` |
| `0x67` | 写 | `[level]` | 先回 `0x67[01]`，随后推送状态 |

### 4.3 音效模式（EQ）

| 命令 | 方向 | 载荷 |
|---|---|---|
| `0xD5` | **读** | 无 → `[slot]` |
| `0xC4` | **写** | `[slot]` → 回 `0xD5[slot]` |

> **易错**：`0xD5` 是读、`0xC4` 是写。反过来会得到"改不动"的错误结论。

Halo 的 `EqType` 是 `0x0E`（`EQ_0E`），**只有 3 个场景**：

| slot | 名称 |
|---|---|
| 0 | 音乐 |
| 1 | 游戏 |
| 2 | 电影 |

自定义 EQ（Halo 未在界面暴露）：

| 命令 | 用途 |
|---|---|
| `0x43` | 读频段表 |
| `0x44` | 写自定义 EQ |
| `0x45` | 重置 EQ |
| `0x46` | EQ 开关 |

频段表实测（`0x43` 响应）：`60 / 100 / 200 / 500 / 1000 / 2000 Hz`，
每段 2 字节小端（如 `0x003C` = 60、`0x07D0` = 2000）。

### 4.4 灯效（核心）

| 命令 | 方向 | 说明 |
|---|---|---|
| `0x6A` | **读** | 读取整个灯效表 |
| `0x6B` | **写** | 写入一条灯效记录 |
| `0x70` | 写 | 灯效关闭 |
| `0x72` | 写 | 灯效重置 |

> **易错**：`0x6A` 是读、`0x6B` 是写。反过来只会收到 `[00]`，
> 容易误判为"灯效只读"。

#### `0x6A` 响应布局

```
[light_array_index, current_light_index, <6 字节记录>...]
        payload[0]         payload[1]
```

每条记录 6 字节：

```
[index, R, G, B, Brightness, Speed]
```

- **解析起点**：`0x6A` / `0x72` 从偏移 **2** 开始走；其他命令从偏移 1 开始
- **1 字节响应 `[00]`** = 设备当前不持有任何记录（氛围灯已关闭）

#### `0x6B` 写入载荷

基础 7 字节（`mood_lighting_splice`）：

```
[array_index, index, R, G, B, Brightness, Speed]
```

第 8 字节 `mode` 可选，仅在需要时附加。

#### Halo 的实测灯效表

```
array_index = 8
index 1..7  = 七个效果
index 8     = 氛围灯总开关
```

实测样例（`0x6A` 响应）：

```
08 01 01 FF E6 FE 64 FF   02 01 00 00 64 06   03 B1 39 FF 50 09
04 8A 95 FF FF FF         05 00 00 00 64 FF   06 C0 FF F2 64 FF
07 FF 40 DB 64 FF         08 00 00 01 FF FF
```

### 4.5 智能灯效（Halo 未在界面暴露）

| 命令 | 用途 |
|---|---|
| `0x84` | 查询 |
| `0x85` | 设置 |
| `0x86` / `0x87` | 配置 |

### 4.6 其他

| 命令 | 用途 |
|---|---|
| `0x07` | 恢复出厂设置 |
| `0xCE` | 关机 |
| `0x62` | 输入源切换 |
| `0xBB` | 蓝牙名称 |
| `0xBC` | 蓝牙地址 |
| `0x6F` | 内置提示音 |
| `0xFA` | 提示音 |
| `0xF8` | LED |
| `0xC1` | ANC |

> `0x07`（恢复出厂）触发后设备会重启，句柄失效，需要重新枚举。

## 5. `0xD8` 功能位图

**它不是位域，而是一张字节表**，长度 22 字节。多数条目读**一位**
（`b0[i]`，其中 `b0 = format(byte, '08b')`，**索引 0 是最高位 MSB**），
少数条目**直接取值**。

| 字节 | 字段 | 读法 |
|---|---|---|
| 1 | `bat` | 直接取值；`!= 0` 才 `is_support_show_battery` |
| 2 | `is_support_query_name` | `b0[7]` |
| 3 | `num_support_set_name` | **直接取值**（名称长度上限） |
| 4 | `is_support_query_mac` | `b0[7]` |
| 5 | `is_support_query_device_version` | `b0[7]` |
| 6 | `is_support_disconnect_a2dp` | `b0[7]` |
| 7 | `is_support_repair` | `b0[0]` |
| 8 | `is_support_auto_shutdown_without_audio_input` | `b0[0]` |
| 9 | `time_off` | **直接取值** |
| 10 | `is_support_device_off` | `b0[7]` |
| 11 | `is_support_show_manual` | `b0[7]` |
| **13** | **`eq`（EqType 值）** | **直接取值** |
| 14 | `skin` | `b0[4]` |
| 16 | `tap` | `b0[0]` |

**这两个"直接取值"的条目最容易误判**：字节 13 是 `0x0E` 而不是 0/1（它是 EQ 类型），
字节 3 是 `2`（名称长度上限，不是标志位）。

### Halo 实测解码

原始位图：

```
00 00 01 02 01 01 01 00 00 00 01 01 0A 0E 0A 00 00 20 00 83 00 20
```

| 字节 | 值 | 结果 | 含义 |
|---|---|---|---|
| 1 | `0x00` | 0 | 不显示蓝牙电量 |
| 2 | `0x01` | **1** | 支持查询名称 |
| 3 | `0x02` | 2 | 名称最长 2 字符 |
| 4 | `0x01` | **1** | 支持查 MAC |
| 5 | `0x01` | **1** | 支持查固件版本 |
| 6 | `0x01` | **1** | 支持断开 A2DP |
| 7 | `0x00` | 0 | 不支持重新配对 |
| 8 | `0x00` | 0 | 不支持无音频自动关机 |
| 9 | `0x00` | 0 | 自动关机时间 |
| 10 | `0x01` | **1** | 支持关机 |
| 11 | `0x01` | **1** | 显示说明书 |
| **13** | **`0x0E`** | **0x0E** | **EQ 类型 = `EQ_0E`** |
| 14 | `0x0A` | **1** | 支持皮肤 |
| 16 | `0x00` | 0 | 不支持敲击 |

## 6. 灯效表（`EA_08`）

Halo 的 `light_array_index = 8`，命中 `EffectArrayType.EA_08`。七个效果及其可用性
**直接从 `EA_08` 的字节码常量读出**：

| index | 名称 | `rgb_settable` | `rate_settable` | `brightness_settable` |
|---|---|---|---|---|
| 1 | 纯色静光 | ✅ | ❌ | ✅ |
| 2 | 幻彩潮汐 | ❌ | ✅ | ✅ |
| 3 | 氛围呼吸 | ✅ | ✅ | ✅ |
| 4 | 声光律动 | ✅ | ❌ | ❌ |
| 5 | 炫彩涟漪 | ❌ | ❌ | ✅ |
| 6 | 纯光回旋 | ✅ | ❌ | ✅ |
| 7 | 辉光渐展 | ✅ | ❌ | ✅ |

`brightness_magnification = 10`。

### `EffectArrayType` 枚举

```
EA_01=1  EA_02=2  EA_03=3  EA_06=6  EA_07=7  EA_08=8  EA_09=9
EA_0C=12 EA_0D=13 EA_10=16 EA_12=18 EA_13=19 EA_1A=26
```

### 氛围灯总开关：写入正确，但**确认不可靠**

`0x6B [array, 8, 0, 0, b, 255, 255]` 的载荷是**正确**的，设备也确实会应用。
但实测发现确认过程不可靠：

- 连续 10 次交替写入（每次写完静置 1.2–2.5 秒再读），**只有 5 次读回期望值**，
  其余读回的是**上一次**的状态
- 单纯延长等待不能解决（静置 1.5 秒、中间不发任何其它命令，仍然 5/8 失配）
- **重写同一个值是有效的**：失败后再写一遍就会生效

所以实现里采用**写入 → 短等 → 读回校验 → 不符则重写**（最多 3 次）。
不要依赖单次写入后的立即回读。

#### `0x72` 是**切换**，不是幂等重置

一个诱人的"修复"是每次开灯前先发 `0x72`。**实测证明这会帮倒忙**：
在两次连续往返中，第二轮的开关结果被反转（`off -> b=1`、`on -> b=0`）。

`0x72` 确实能让"设备不持有任何记录"的状态恢复（`0x72 [8, 1]` 一次性恢复 8 条记录），
但它带切换语义，**不能无条件地跟着开关一起发**。

### 关键细节

**亮度与速度的缩放方式不同**（这是最容易出错的地方）：

| 参数 | wire 编码 | UI 值 ↔ wire |
|---|---|---|
| 亮度 | UI × 10（0–100） | `wire = ui * 10`，`ui = (wire + 5) / 10` |
| **速度** | **直接值（1–10）** | **`ui = wire`，无缩放** |

若把亮度的 ÷10 公式套到速度上，设备报 `sp8`（速度 8）会被显示成 `1`，
表现为"速度永远是 1"。

**`255` 是哨兵值**：表示"该参数不可调"。读到时控件应禁用。

**活动效果取自 `payload[1]`**，不是第一条记录。设备经常在选中效果 2/3 时仍然把
记录 1 列在最前，而记录 1 恰好不支持调速——用错来源会导致速度控件误判为不可用。

**氛围灯总开关**：`EA_08` 用 `index = 8` 表示总开关，而**开关状态存放在记录的
`b` 字段**，不是 `speed`：

```
读：g.b == 1  → 开
写：[array_index, 8, 0, 0, on ? 1 : 0, 255, 255]
```

放在 `speed` 里会导致"能关不能开"（关灯后 `b` 恒为 0）。

## 7. 实战注意事项

### 7.1 设备有小命令缓冲区

**密集查询会把设备打到静默**，表现为 `0x6A` 返回 `[00]`。实测需要**静置约 8 秒**才能恢复，
同一进程内重新打开句柄不一定能救回来。

正确做法：**每次只发一条命令，用短超时**，不要连续轰炸。

### 7.2 写入后需要等待

灯效类写入（`0x6B`）大约需要 **900 ms** 才会在 `0x6A` 中反映出来。
过早回读会拿到**写入前的旧值**。

| 命令类型 | 建议等待 |
|---|---|
| 灯效 `0x6B` / `0x72` | 900 ms |
| 恢复出厂 `0x07` / 关机 `0xCE` | 1400 ms |
| 其他 | 120 ms |

### 7.3 恢复出厂后必须重新枚举

`0x07` 会让设备重启，原句柄失效。需要重新 `find` + `open`，
并且**不能假设原路径仍然有效**。

### 7.4 实时同步靠轮询

官方客户端**不读取任何硬件状态推送**——实测（Frida 挂钩 100 秒）官方客户端在
USB 通道上**零次 HID 读/写/ioctl**，它走的是另一条路。

要在自己软件里反映"别处改动的状态"，只能**定向轮询单条命令**：

| 内容 | 命令 | 周期 | 单次超时 |
|---|---|---|---|
| 音量 | `0x66` | 150 ms | 120 ms |
| 灯效表 | `0x6A` | 300 ms | 160 ms |
| 音效模式 | `0xD5` | 400 ms | 140 ms |

每次只发一条，**按最超期者优先**。用 `if/else if` 链会让 150 ms 的音量把 300/400 ms
的两项**饿死**。另外**处理了写命令的那一轮要跳过轮询**，否则拖动滑条会被轮询拖慢。

### 7.5 氛围灯关闭时设备不上报灯效表

此时 `0x6A` 返回裸 `[00]`。这意味着：

- **无法从设备回读开关状态**，"有没有记录"本身就是开关状态
- 但 **`array_index` 要保留上一次的有效值**，否则重新开灯时写入会用到错误的灯组

## 附：灯效表记录的精确字节布局（实测复核）

`0x6A` / `0x72` 应答的载荷结构，已用原始帧逐字节核对：

```text
2F BB EC 6A 00 32 | 08 01 | 01 FF E6 FE 64 FF | 02 01 00 00 64 0A | ...
└──── 6 字节帧头 ──┘ └ 头 ┘ └──── 记录 1 ────┘ └──── 记录 2 ────┘
                    ↑      ↑
              array_index  current_index
```

| | 长度 | 组成 |
|---|---|---|
| **应答记录** | **6 字节** | `[idx, R, G, B, brightness, speed]` |
| 应答载荷 | 50 字节 | `2 + 8 × 6`（8 个条目：7 个效果 + 索引 8 的总开关） |
| **写入载荷** | **7 字节** | `[array_index, idx, R, G, B, brightness, speed]` |

### 这里容易踩的坑

**`mode` 字节在本设备上不存在。** 官方解析表里 `mode` 是**可选的第 7 个字段**，
只对部分机型有效；Halo Soundbar 的应答里没有它。

如果按 8 字节步长硬解析（`idx, R, G, B, bri, spd, mode, align`），
得到的会是**看似合理但完全错误**的数值：

```text
错误解析（步长 8）           正确解析（步长 6）
idx= 1 rgb=FFE6FE bri=100 spd=255 mode=2     idx=1 rgb=FFE6FE bri=100 spd=255
idx= 0 rgb=00640A bri=  3 spd=255 mode=0     idx=2 rgb=010000 bri=100 spd= 10
idx=100 rgb=06048A bri=149 spd=255 mode=255  idx=3 rgb=FF0000 bri=100 spd=  6
```

注意错误版本里的 `idx=100`、`idx=255` —— **索引不可能大于 8**，这是最快的判别方法。
另一处线索是 `bri=100 spd=255`：速度字段出现 `255` 表示"不可调"，
但如果亮度也是 100 而速度是 255，就要怀疑字段错位了。

### 各条记录的语义

| idx | 含义 | bri/spd 为 255 表示 |
|---|---|---|
| 1–7 | 七个灯效 | 该效果不支持调节该项 |
| **8** | **氛围灯总开关** | bri/spd 恒为 255，无效 |

索引 8 的记录形如 `[08, 00, 00, b, 255, 255]`，
开关状态在**第 4 个字节（即蓝色字段位置）**：`b == 1` 为开。

读取时应按**索引值**查找记录（`iter().find(|r| r.index == 8)`），
不要用固定下标——设备不保证顺序，也不保证一定返回 8 条。
